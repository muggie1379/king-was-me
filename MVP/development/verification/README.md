# 검증 하네스 사용법

이 폴더는 KING WAS ME HTML MVP 빌드를 "실제로 실행해서" 검증하기 위한 재사용 가능한 도구 모음입니다. GPT(또는 다른 누구든)가 새 버전을 넘겨줄 때마다, 코드를 읽는 것만으로는 잡히지 않는 버그(런타임 크래시, 분기 로직 오류, 함수값이 문자열로 resolve되지 않는 문제 등)를 실제 headless 실행으로 잡아내기 위한 것입니다.

이 대화에서 이 방식으로 실제로 잡아낸 버그가 최소 4건 있습니다 (자세한 내용은 `../00_START_HERE.md`의 "알려진 버그 / 수정 이력" 참고). 코드 리뷰만으로는 이 중 다수를 놓쳤을 것입니다.

## 사전 준비

Node.js만 있으면 됩니다 (브라우저, npm 패키지 불필요). 이 폴더의 파일들은 순수 Node로 동작하는 최소 DOM 스텁 위에서 게임의 `<script>` 코드를 그대로 `require()`해서 실행합니다.

## 사용 순서

```bash
cd verification/

# 1) 검증하려는 HTML 빌드에서 두 개의 <script> 블록을 script1.js / script2.js로 추출
node extract.js ../KING_WAS_ME_MVP.html
# (또는 새로 받은 파일 경로로)

# 2) 문법 체크 (가장 기본, 하지만 이것만으로는 부족함 — 아래 "주의" 참고)
node --check script1.js
node --check script2.js

# 3) 전체 플레이스루 회귀 테스트 (1회차 + 2회차, 처음부터 엔딩까지)
node driver.js

# 4) 타임아웃 이벤트 전용 테스트 (20초 타이머를 실제로 기다리지 않고 시뮬레이션)
node driver_timeout.js
```

각 드라이버는 문제를 발견하면 `FAIL:`로 시작하는 메시지를 출력하고 exit code 1로 종료합니다. 아무 `FAIL`도 없이 `all checks passed.`가 뜨면 기본적인 실행 경로는 안전하다는 뜻입니다.

## 이 도구가 확인해주는 것 / 확인해주지 못하는 것

**확인해주는 것:**
- 스크립트가 로드 시점에 크래시하지 않는지 (문법 오류, 정의되지 않은 함수 호출 등)
- 1회차·2회차 모두 처음부터 실제로 엔딩까지 도달 가능한지 (막다른 분기가 없는지)
- 타임아웃(20초 타이머) 이벤트가 실제로 트리거되고, 정해진 대체 선택지가 나타나는지
- "함수값이 문자열로 resolve 안 되는" 버그 클래스 (v6.4~v6.5.1에서 3곳 발견됐던 것과 같은 종류) — `eventTitle`/`chronicle`/`s2EventTitle`/`s2Chronicle`에 raw JS 함수 소스가 텍스트로 노출되는지 자동으로 스캔
- 2회차 타임아웃에 "지금 결정한다" 같은 되돌리기 버튼이 실수로 다시 생기지 않았는지 (의도적으로 1회차와 다르게 설계된 부분이므로)

**확인해주지 못하는 것 (사람이 직접 봐야 함):**
- 텍스트 내용 자체의 품질, 톤, 캐릭터 일관성
- 새로 추가된 분기/이벤트가 기존 디자인 원칙(왕은 말하지 않는다, 숨겨진 수치 노출 금지, 기행 선택지 2회 상한 등)을 지키는지 — `00_START_HERE.md`의 원칙 목록과 대조해서 직접 diff를 읽어야 함
- GPT가 "이런 것만 바꿨다"고 주장한 범위가 실제로 맞는지 — 이건 `diff`로 확인 (아래 참고)

## "claimed 범위" 검증 습관 (diff)

새 버전이 올 때마다, 실행 테스트와는 별개로 반드시 이전 버전과 diff를 떠서 GPT가 말한 변경 범위와 실제 변경 범위가 일치하는지 확인하세요. 이 대화에서 실제로 v6.1이 "1회차는 그대로 유지"라고 주장했지만 실제로는 1회차 대사 태그 158곳이 의도치 않게 바뀐 것을 diff로 잡아낸 적이 있습니다.

```bash
# 이전 버전과 새 버전 각각에서 extract.js로 script1.js/script2.js를 뽑은 뒤
diff old_script1.js new_script1.js
diff old_script2.js new_script2.js
```

diff 결과가 GPT의 설명과 안 맞으면(예: "이 두 줄만 바꿨다"고 했는데 diff가 수백 줄이면), 그 자체가 조사해야 할 신호입니다.

## 새 이벤트/구조가 추가됐을 때 이 드라이버를 고쳐야 하는 경우

- `domstub.js`의 `ids` 목록에 없는 새 DOM id를 게임 코드가 참조하면, `getElementById`가 자동으로 빈 `El`을 만들어주므로 크래시는 안 나지만, 그 요소를 기대하는 테스트 로직은 조용히 틀린 값을 볼 수 있습니다 — 새 패널/모달이 추가되면 `ids` 목록에 추가하는 걸 권장합니다.
- `driver_timeout.js`는 타이머 이벤트를 이벤트 제목 텍스트(`'취소된 약속'`)로 찾습니다. 이 이벤트의 이름이 바뀌거나, 타이머가 다른 이벤트로 옮겨가면 `TIMED_EVENT_TITLE` 상수를 갱신하세요.
- 두 드라이버 모두 "항상 첫 번째 선택지를 클릭"하는 방식으로 진행합니다. 이건 크래시 여부와 엔딩 도달 여부만 확인하는 것이고, 특정 분기(예: `pause_contact`/`pull_back_real` 같은 "강한 선택 → 강한 분기" 경로)를 확인하려면 별도로 임시 드라이버를 짜서 원하는 선택지 id/텍스트를 명시적으로 클릭하도록 수정해야 합니다. (이번 대화에서 v6.4/v6.5.2 검증 때 실제로 그렇게 했습니다 — 필요하면 이 파일들을 복사해서 특정 분기용으로 변형하는 걸 추천합니다.)
